# Sample Performance Report

> Note: Actual values will change depending on system speed, JVM state, and Derby cache. Use the output generated by option 10 in the application for your final screenshot/report.

| Operation | Records | Avg Time (ms) | Throughput | Observation |
|---|---:|---:|---:|---|
| Individual executeUpdate() insert | 1000 | 800 | 1250 ops/sec | Simple but slower because each insert is executed separately. |
| Batch addBatch()+executeBatch() insert | 1000 | 250 | 4000 ops/sec | Faster because multiple rows are handled together. |
| Statement string concatenation | 1000 | 700 | 1428 ops/sec | Less safe and involves repeated SQL string creation. |
| PreparedStatement parameterized insert | 1000 | 520 | 1923 ops/sec | Safer and may reuse compiled execution plan. |
| Commit per operation | 100 | 300 | 333 ops/sec | Slower due to repeated commit/log overhead. |
| One commit for 100 operations | 100 | 80 | 1250 ops/sec | Faster because commit overhead is reduced. |
| Indexed lookup on Loans.MemberID | 1000 | 100 | 10000 ops/sec | Uses index and works better for selective queries. |
| Full-table scan on Loans | 1000 | 250 | 4000 ops/sec | Reads the full table and slows down as data grows. |

## Observations

1. Batch inserts are faster than individual inserts.
2. PreparedStatement is safer and generally more efficient than Statement.
3. Grouped commits perform better than committing after every operation.
4. Indexed lookup is faster than full-table scan when searching by member ID.
5. Derby cache and JVM warm-up can affect initial benchmark results.
